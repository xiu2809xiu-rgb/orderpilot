# ADR 0012: Sessions and role-based access

- **Status:** Accepted
- **Date:** 2026-10-31
- **Story:** P-10

## Context

Every area needs to know who is calling and what that person may do, and the panel will test it: a direct API call must be refused and the refusal must show in the audit trail (E2E #3). The web app (P-11) was built first, against the routes in `packages/shared/src/auth-routes.ts`, so the paths, the cookie and header names and the schemas are fixed. This decision fills in what is behind them.

## Decision

1. **Passwords use argon2id,** through `@node-rs/argon2` at the OWASP minimum cost (19 MiB, 2 passes, 1 lane). It ships prebuilt binaries and runs no install script, so it needs no entry in `allowBuilds`; the `argon2` package builds with node-gyp. A test checks the `$argon2id$` prefix. Sign-in always verifies a hash: an unknown user, or an account with no password, is checked against a dummy hash, so both answer `INVALID_CREDENTIALS` in about the same time. A disabled user gets the same answer, and the audit event says why.
2. **The access token is a JWT** signed with HS256 by `jose`, valid for 15 minutes (`ACCESS_TOKEN_TTL_SECONDS`). Verification pins the algorithm, the issuer and the audience, so `none`, HS512 and a token for another audience are refused. The claims are the user id, the sign-in's family id (`sid`) and the demo flag. The role is not in the token: the guard reads the user on every request, so a role change or a disabled account takes effect at the next request, not in 15 minutes. It also checks that the sign-in still has a live refresh token, so sign-out, a reuse and disabling a user end the access token at once.
3. **The refresh token is opaque,** 256 random bits. Only its SHA-256 is stored (`RefreshToken.tokenHash`), so a leaked table cannot be replayed as cookies. Each use rotates it: the old row gets `usedAt` and a successor, in one transaction that locks the row (`FOR UPDATE`), so two requests with the same token take turns. Presenting a token that was used already revokes every token of that sign-in (`revokedReason: reuse-detected`), writes `auth.refresh.reuse-detected` to the audit trail in the same transaction, and answers `REFRESH_REUSED`. The refusal is returned from the transaction, not thrown, so the revocation commits. The lifetime slides: each rotation gives a new 7 days (`REFRESH_TOKEN_TTL_SECONDS`). A `demo` column on `RefreshToken` (migration `20261031100000_refresh_token_demo`) keeps the demo flag across refreshes.
4. **Three cookies,** named by the shared contract: `op_access` (httpOnly, path `/`), `op_refresh` (httpOnly, path `/api/v1/auth`, so the browser sends it nowhere else) and `op_csrf` (readable by script, path `/`, as long as the refresh token, which also tells the web app after a reload that a session may be open). All are `SameSite=Strict`: the web app and the API share a site behind the proxy. **Secure is on everywhere** except `APP_ENV=local` with `COOKIE_SECURE=false`, which `.env.example` sets so plain `http://localhost` works in every browser (Safari ignores a Secure cookie on http). The API refuses to start with `COOKIE_SECURE=false` under `demo` or `production`.
5. **CSRF is a signed double-submit.** The CSRF token is `nonce.HMAC(nonce)` under the JWT secret. The guard needs the cookie and the `X-CSRF-Token` header to be equal and the signature to verify, so an attacker who can plant a cookie (a sibling subdomain) still cannot mint a token. It applies to every unsafe method. Only `login` and `demo-login` are exempt (`@SkipCsrf()`): no session exists yet for a forged request to ride on. `refresh` and `logout` need the header, as the contract says.
6. **Deny by default, in four global guards, in this order:** the rate limiter, the auth guard (who are you), the CSRF guard (is it really our page), the permissions guard (may you). Every route must say one of three things, and a route that says nothing is refused with 403 even for a signed-in user, so a forgotten decorator fails the first time the route is called:
   - `@Public()`: no session needed (the health probes, the auth routes that start or end a session, `system/checks`). Swagger UI is mounted outside Nest's controllers, so the guards do not see it; it has its own switch (`SWAGGER_ENABLED`).
   - `@Authenticated()`: any signed-in user (`GET /auth/me`).
   - `@RequirePermission("users.read")`: a signed-in user whose role holds the permission.
7. **The permission check sits behind one class,** `PermissionPolicy` (`decide(request) -> { allowed, reason }`). The default, `MatrixPermissionPolicy`, asks the `RolePermission` table, which area 4 owns and edits. F-1 and F-3 add limits, segregation of duties and data scope by providing their own policy under that token; the request carries the user, the permission, the method, the path and the route parameters. No controller changes. The names are in `@orderpilot/shared`, and so is `DEFAULT_ROLE_PERMISSIONS`, which the seed writes and the web app's tests read.
8. **Refusals are audited, with a rule against flooding.** Audited: a bad sign-in (`auth.login.refused`, `auth.demo-login.refused`, without the attempted email, which may be a mistyped password), a refused refresh, a reused refresh token, an access token that is forged, malformed or for a user who is disabled, unknown or signed out (`auth.access.refused`), a failed CSRF check by a caller holding a session (`auth.csrf.refused`) and every refused permission (`auth.permission.refused`, with the user, the role, the route and the permission). **Not audited:** a call to a protected route with no session cookie at all, and a call whose access token has merely expired (the web app refreshes silently, so that happens every 15 minutes). Both are in the request log with the trace id. **Sampled:** a refusal that anyone can cause with junk and no account (a token that does not verify, a CSRF failure with no session, a sign-in sent as a form or from a foreign origin) is written at most once a minute per client address and action; the rest are in the request log only. The entity of such a row is the route pattern, cut to 200 characters, never the raw path. Successful sign-in and sign-out are audited (`auth.login`, `auth.demo-login`, `auth.logout`) in the same transaction as the change; a successful refresh is not (it would write one event per user per 15 minutes). A refusal changes nothing, so it is audited on its own; if that write fails, the caller is still refused and the failure is logged.
9. **The demo sign-in exists only when `DEMO_MODE` is on.** `AuthModule.register(config)` adds `DemoAuthController` only then, so with it off the route answers 404 like any unknown path and is absent from Swagger. `GET /auth/options` tells the sign-in page which it is. `APP_ENV=production` refuses to start with `DEMO_MODE=true`, with the default JWT secret (the one in `.env.example`, which is public) or one shorter than 32 characters, with `COOKIE_SECURE=false`, and with `DEMO_PASSWORD` set. The OpenAPI file is exported with `DEMO_MODE=true` so it documents the route.
10. **Sign-in has its own, stricter rate limit** (`AUTH_RATE_LIMIT_MAX_REQUESTS`, 20 per window against 300 for the rest), counted per client address on `login` and `demo-login` only.
11. **Users are disabled, never deleted.** Disabling sets `disabledAt`, revokes every refresh token of the user and writes `user.disabled` in one transaction; an administrator cannot disable their own account. Enabling writes `user.enabled`. Doing either twice changes and audits nothing.
12. **Seeds are idempotent.** The matrix is filled with the pairs that are missing (a pair area 4 removed comes back on the next seed; `ON CONFLICT DO NOTHING` never overwrites). One user per role, with the synthetic names and `*.example.test` addresses. Their password is `DEMO_PASSWORD`, with a default in `.env.example` for laptops and demos only; without it the accounts have no password.

## Consequences

- A new route is one decorator and, for a list or a write, one permission name. CONTRIBUTING shows it once.
- The guard does two small reads per request (the user, and whether the sign-in is live). That buys instant revocation. A cache can come later behind the same guard if it ever shows up in a trace.
- **Two tabs can race.** Both may refresh the same token at the same moment; the second is treated as a reuse and ends the sign-in. A short grace window for the previous token is the usual fix. It weakens "a reused token revokes the family", so it is not in this story; it is on the backlog with the web app's refresh timer in mind.
- The refresh lifetime slides with no absolute cap, so a sign-in that is used every week never ends. An absolute cap (and a "sign out everywhere" button) are on the backlog.
- Rate limiting is per address, in memory, per API process. With more than one process it needs Redis (the throttler supports it); `TRUST_PROXY_HOPS` must be right behind a proxy or every client shares one address.
- **Login CSRF is closed by content type and origin, not by a token.** `login` and `demo-login` take only `application/json` and refuse an `Origin` that is neither on `CORS_ORIGINS` nor the request's own host, so a cross-site HTML form cannot swap a victim's session for the attacker's.
- **The CSRF token is signed but not bound to a session.** An attacker who can plant cookies from a sibling subdomain could plant a valid token copied from their own sign-in. The custom header and the CORS preflight still stop a forged cross-origin request. Binding the token to the session id is on the backlog.
- **A demo session ends when `DEMO_MODE` is turned off:** the guard refuses it and a refresh revokes its family. The guard also checks that the sign-in belongs to the user in the token. `APP_ENV` other than `local` refuses the default JWT secret.
- Rotating `JWT_SECRET` signs everyone out (access tokens fail, CSRF tokens fail; the refresh tokens survive and a refresh with a fresh CSRF cookie is not possible, so users sign in again). That is acceptable for now.
- Nothing creates the first real administrator in production: the seeded accounts have no password there. A one-time bootstrap command is on the backlog; until then production is not usable, and nothing claims it is.
- The audit trigger stops accidents, not the database owner. A non-owner runtime role (ADR 0010) is on the backlog under epic F.

## Alternatives considered

- **Sessions in Redis instead of JWTs.** Simpler revocation, but the guard already reads the database on each request for the same effect, and a JWT keeps the web contract (`expiresAt`, silent refresh) honest.
- **`argon2` (node-gyp) or bcrypt.** The first needs a reviewed build script; bcrypt truncates at 72 bytes and is not memory-hard.
- **A plain double-submit cookie.** Easier, but a planted cookie defeats it. The signature costs five lines.
- **`@UseGuards` on each controller.** A forgotten one is open. A global guard that refuses the unmarked is closed by default.
