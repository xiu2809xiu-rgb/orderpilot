# ADR 0060: Spark and its read-only tools

- **Status:** Proposed. Spark's module is area 1's, and it touches area 4's permission matrix, its refusal wording and its destination check, so Richie accepts or declines it in review, with Angelyn's review of those three.
- **Date:** 2026-11-22
- **Story:** [#345](https://github.com/xiu2809xiu-rgb/orderpilot/issues/345), step 1 of P-95 ([#233](https://github.com/xiu2809xiu-rgb/orderpilot/issues/233)). Amends [ADR 0059](0059-the-ai-gateway-and-the-person-in-the-loop.md): its consequence "Spark does not use the gateway yet" is replaced by this record.

## Context

Spark answers in the browser today, from two scripted answers. Richie asked on 21 Nov for Spark on a real model. ADR 0059 put one gateway in the API (the mock by default, a destination check, a fenced tool loop, a usage record per call), and it said Spark would use it in P-95. This step gives Spark its server side and changes nothing in the web, so the demo stays as it is.

A design for P-95 was written and then read against the code by a second reader. Their findings that decide this record: the services behind the tools return rows that carry more than a question needs (a vendor, a customer's own reference, a cost); in a demo everyone of a role signs in as one user; a model's earlier answer, replayed to it, is a way for text from a record to reach it unfenced; the origin of the data cannot be derived from the tools, because stored orders can be typed in by staff; a crash between the question and the answer would strand a thread; and a model route has no cost limit of its own.

## Decision

1. **Conversations are a person's own.** `SparkConversation` and `SparkMessage` hold them. Another person's conversation answers 404, with the same body as an unknown id, so a probe learns nothing. In a demo session, where every sign-in of a role is one user, conversations are kept per session (`sessionId`), so a tester cannot read another's questions. A conversation is archived, never deleted: the audit trail holds only a sha256 and a length of the text, so a kept row is what lets a reviewer compare the text with its hash. An archived conversation reads as 404.
2. **A permission, `spark.use`.** Every role but the System admin holds it by default. The System admin is refused with 403, and the refusal is audited. It is not on the locked "never for the System admin" list, because that list is area 4's and was not asked for; it is only absent from the administrator's defaults. A new permission reaches an existing database through the role-permission seed, and a signed-in session has it from its next sign-in.
3. **Three read-only tools, `check_stock`, `find_orders` and `get_order`.** Each is made with `defineReadOnlyTool` for one question, asks for one permission (`orders.read`, the one of the routes it reads), and runs as the person asking: it passes that person's role to the service, which masks by role. A tool builds its result by naming each field it keeps. A service's row is never spread or passed through, so a field added to a service later reaches the model only when a reviewer sees it added. Left out on purpose: vendor and bank data, cost, the customer's own document number, the Navision number, the prepayment and the version. A hidden price or amount is handed over as `hidden` with its reason, never as a value. A result is capped (five items, ten orders, twenty lines, a description cut at 120 characters) to stay well under the 20,000 characters at which the tool loop cuts a result and breaks its JSON, and a test holds it under 12,000 with the worst input. An unknown order is a plain result, not an error, so the model can tell a typo from an outage. The tools are not reachable except from the toolset, and the module's import guard (see 9) lists the two read services they call.
4. **The sources are what the tools returned.** The same projection that is handed to the model is handed to the run's collector, which keeps each record once (twenty at most). The app labels them as what Spark looked at. They are not proof that the answer's prose used them, and they are built by the server, never from the model's words. The model writes the prose and nothing else.
5. **The labels are true, and fail closed.** The gateway believes the classification and origin it is told. Spark declares `confidential` and takes the origin from one setting, `DATA_ORIGIN`. Unset or blank counts as synthetic, any word other than `synthetic` or `real` stops the API from starting, and `APP_ENV=production` refuses to start without the setting, so that a real deployment that forgets the line cannot tell the policy its data is synthetic. Only inside Spark does a value it cannot read count as real (an unreadable setting fails closed), and with a real origin Spark is refused for every provider, the offline mock included, until area 4 adds a rule: the default policy trusts no provider with real data. The Docker stack passes `DATA_ORIGIN` into the API and the worker as it is, with no default of its own, and the client-samples stack always says `real`, so that stack fails closed. The person's own typed question goes to the provider too, so it is covered by the same setting.
6. **History cannot carry an injection.** Earlier turns go back as the person's own words, and Spark's earlier answers go back only as a sentence the server writes: the tools that ran and the kind and id of each record read, kept only when they look like names and ids. The prose of an answer and a source's label are never replayed, because both can carry text from a record. A tool's result is fenced as data by the gateway, and is not stored in the conversation, so it cannot reach a later turn at all.
7. **One answer at a time, and no stuck thread.** A question is two small transactions around the gateway call, which refuses to run inside one: the question and its audit event, then the answer and its audit event. A pending question (a question with no answer after it) answers a second one with 409, and the unique key on the sequence number is what holds when two arrive together (its violation is a 409, not a 500). A pending question older than the gateway's own worst case (the time limit times the attempts times the tool rounds plus one) is closed as failed with the code `abandoned`, so a crash never blocks a thread. With the defaults (60 seconds, 3 attempts, 5 tool rounds) that is 60 x 3 x 6 = 1,080 seconds, 18 minutes: after an API restart in the middle of a question, that conversation answers 409 for up to 18 minutes. It is not shorter because the gateway has no overall deadline of its own, so a question closed as abandoned sooner could still have its provider call running, and a second question could then be accepted beside it. A shorter limit is a setting change away if Richie asks for one.
8. **Cost is bounded.** The question route has a named throttler, `spark` (default six a minute), and a person has a daily cap (default a hundred, counted over the last 24 hours across all their conversations), refused with the existing `RATE_LIMITED`. Both are settings. The per-minute limit is keyed by the caller's IP address and runs before the sign-in check, so it counts refused calls too (a 401, a 403, a 404 or a 400 use up the same six). The daily cap is keyed by the user, so in a demo, where every sign-in of a role is one user, the testers of that role share the hundred, and testers on one address share the six a minute. The keys are not changed: keying the cap by session would let a new sign-in give a fresh allowance and weaken the cost bound. The daily cap bounds the cost and is not an exact meter: two questions that arrive together can both pass the count.
9. **Only read services.** An import guard, like the gateway's, lists every file outside `modules/spark` that the module may reach, with a reason, and fails on a new one. It names `OrdersService` and `MasterDataService` and no other service of orders or master data. A second control sits behind it: `OrdersModule` exports the reader and never `OrdersWriteService`, which a test checks. Prisma is reached only from the repository.
10. **Every answer is audited and kept, and a failure is an answer.** The question and the answer each write an audit event, with a sha256 and a length and no text, the tools asked for and the refused ones, the number of sources, the provider and the model. A refused destination, a provider failure, an abandoned question and a refused tool are stored as a failed answer with a safe code (`refused`, `timeout`, `provider-error`, `invalid-output`, `too-many-steps`, `internal`, `abandoned`), still a 201, never an error page. A destination refusal is `refused` only: the rule stays in the audit row and the usage record. A tool of Spark's that was refused and never ran afterwards makes the whole answer a failed one with the code `refused`: the model would have written it without what was asked for, and the person is told that and not given its guess. So `refused` covers a destination refusal and also any refused call of Spark's own tools that was never put right, whatever the kind of refusal (an unknown tool, bad arguments, too many calls, or a role without the permission). A refusal the model got round (bad arguments, then good ones) is a recovery, and a tool name the model made up is refused and audited by the loop without failing the answer. A tool step with the status `failed` (the tool threw) is different: it leaves an OK answer, and the step is the only mark of it.
11. **The usage record is found by the answer's trace id.** The gateway is told `<request id>:<answer id>`, which is stored on the answer, because the request id is the caller's to choose. `AiUsageRecord.traceId` is indexed. Tokens and cost are not on the message: the usage record holds them, and tokens on a failed answer are null.
12. **The steps come from the gateway's stream.** Only `streamText` reports each tool call, including the ones a permission refused, so Spark reads the stream and stores the answer whole. No text reaches the person as it arrives in this step.
13. **The offline mock answers from the tool.** Spark's script is a plain function of the request. It reads the last user message, never `userText` or `turn`, which count earlier turns of the conversation; it tells a first step from a step after a tool by the number of tool results; it takes the JSON out of the fence without relying on the nonce and reads it back through the same zod schema the tool wrote it with; it builds its sentence from that result, so a figure that changes in the data changes in the answer; and for any question it does not know it says what Spark can do, so a missing script or an unknown question never surfaces as an error. No real provider is called by any test.

### Accepted rules

- **A stored answer keeps what the role could see when it was asked.** Each message stores the asking person's role. If the matrix later takes prices from that role, or the person's role changes, the amounts already in an old answer are shown again as they were. They are not re-checked on read. This is accepted for this step, and area 4 may ask for the opposite.
- **Archiving keeps the text comparable with the audit hash.** The audit row holds a sha256 and a length, so deleting the row would not break the chain. The reason to archive is that the stored text can be compared with the hash. Retention, how long a conversation is kept, is not decided.
- **A tool refused for a made-up name does not fail the answer.** Only a refusal of one of Spark's own tools does.

## Alternatives considered

- **Pass a service's result to the model.** It is less code, and every field a service adds would reach a third-party provider. Naming the fields is the control that a new field cannot leak by accident.
- **One permission for Spark and the tools both.** The tool loop asks for the permission of each tool as the person, which is what makes a role change effective for tools too. Each tool asks for the permission of the route it reads.
- **Replay the model's earlier answers, or fence them.** Replaying them lets text that came out of a record reach the model as the assistant's own voice. Fencing them says they are data but still sends them. The sentence the server builds is enough to follow a conversation about records, and carries nothing that came out of one.
- **Delete a conversation.** It would remove the stored text the audit hash is meant to be compared with, and retention is not decided.
- **`generateText` and no steps.** The plain call does not report a refused tool, and the answer to "did a tool get refused" would have to come from the audit trail.
- **Derive the origin from the tools.** Stored orders are typed in by staff, so on a deployment the answer is not "synthetic while every source is the mock". One setting says it, and a production deployment must set it.

## Consequences

- **Spark uses the gateway from this step.** ADR 0059's consequence "Spark does not use the gateway yet" no longer holds for the API. The web still answers Spark from its own scripts, so no person sees a change until a later step of P-95 switches it.
- **A real provider has still been called by no test.** The tests use the mock and fakes. Whether a real model asks for these tools well is not known: a manual check on Richie's key comes before the web is switched.
- **Two known leaks are for step 2, not this step.** The tracker and the exceptions answers already show prices to roles that may not see them (#291), because their services do not mask. Their tools are not in this step, and the leak is raised with Iok Teck before they are.
- **The origin setting is a declaration, as ADR 0059 says of every label.** A deployment that holds real data must say `DATA_ORIGIN=real`, and the question a person types is covered by it. Away from production an unset line reads as synthetic, which is why production must say it either way.
- **The demo stack's database may lack the new permission.** Its reset copies an old template, and a permission reaches an existing database by the seed. The step that turns Spark on in the web gates it by demo or by permission, or re-seeds that stack.
- **The sources are "looked at".** They show what a tool returned. A model's sentence can still state a figure that is wrong beside a correct source, and nothing here checks prose against numbers.
- **Cost is counted from the usage record.** The prices default to 0, so the cost column is not a figure until the `AI_PRICE_*` settings are filled in.
