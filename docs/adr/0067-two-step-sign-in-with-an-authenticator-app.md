# ADR 0067: Two-step sign-in with an authenticator app

- **Status:** Proposed. Sessions and the sign-in page are area 1's, so Richie accepts or declines it in review. Angelyn co-owns the auth code and is asked to review it.
- **Date:** 2026-11-24
- **Story:** [#380](https://github.com/xiu2809xiu-rgb/orderpilot/issues/380)

## Context

Richie asked on 24 Nov 2026 for a one-time code at sign-in, and attached a React bundle, "OTP Input Verification": a pill that unfolds into six cells, folds to "Verifying", then shakes red or turns green.

The bundle is design material, not a part we can drop in. It needs `gsap` 3.12.7, which the app does not have. It imports a constants file (`OTP_MOTION`, `OTP_REPLAY`) that it does not contain, so its timings are not given. It mounts in a shadow root, embeds a font, is light-only, and checks the code against a hard-coded "123456". It states no licence of its own. Its source is a design post by bestsaasdesigns (https://x.com/bestsaasdesigns/status/2111020282551132539).

Where does the code come from? Nothing in the API sends email. The demo accounts' addresses end in `@example.test` and cannot receive any. [ADR 0018](0018-mailpit-for-development-email.md) keeps mail inside Mailpit, and real email is out of scope. An authenticator app works on a real phone with no service behind it.

## Decision

1. **The code comes from an authenticator app** (RFC 6238: HMAC-SHA1, 30 second steps, 6 digits). On screen it is "Two-step verification". The challenge row has a `channel` column, so a second channel could join later without changing the flow. Only `authenticator` is built.
2. **No OTP library and no new variable.** `node:crypto` does HMAC, HKDF and AES-GCM, and base32 is written by hand against the RFC 4648 vectors. The secret (20 random bytes) is stored sealed with AES-256-GCM, under a key derived with HKDF-SHA256 from `JWT_SECRET` and a fixed label, with the person's id as associated data so a sealed value cannot be moved to another person. In plain words, the seal is only as strong as `JWT_SECRET`. On a stack that uses the public default of `.env.example` it is obfuscation, not protection. Production has no `DEMO_PASSWORD` and so no password sign-in ([ADR 0012](0012-sessions-and-rbac.md) items 9 and 12), which means two-step guards the local and demo stacks today. Rotating `JWT_SECRET` makes every sealed secret unreadable: a code is then refused, a recovery code still signs the person in and turns two-step off, and they set it up again.
3. **Verification.** The current step and one either side are accepted. A code works once: the last accepted step is stored for the person and any step at or below it is refused. All time comes from an injected `Clock`, so a test passes one fixed moment.
4. **The challenge.** A right email and password for an account with two-step on gives no session. The API answers `401 TWO_STEP_REQUIRED` in the one error envelope, with `details: null`, and sets an httpOnly cookie, `op_two_step`, SameSite=Strict, on the path of the verify route only, for 5 minutes. It names a server-side challenge row. `POST /auth/two-step/verify` with a code or a recovery code then gives the usual session cookies. A `200` with a second answer shape was rejected: a caller that does not know about two-step must see a non-2xx answer and no session cookie, never a `200` it could mistake for success. The wrong-password answer is unchanged. The login transaction inserts the challenge before it writes its audit row, so a login and a verify for one person at the same time cannot deadlock on the audit chain, and a test holds the chain lock to prove it.
5. **Limits.** Five wrong codes on one challenge end it, and the fifth answers `401 TWO_STEP_CHALLENGE_ENDED` so the page leaves the step at once. Ten wrong codes in 15 minutes for one person lock six-digit entry across every sign-in and the settings routes. The first two locks last 15 minutes. The third in a row lasts 24 hours. A success clears the count. A flat 15 minutes would let someone who knows the password reach about 8% over 30 days (3 of 1,000,000 codes are accepted per try, and 960 tries a day are possible); with the long lock it is about 0.1%. The tries are counted afresh once a lock is placed. The wrong code that places a lock, when it is not the fifth of its challenge, answers `422`, and the next code answers `429 TWO_STEP_LOCKED`. Every such `429` carries `Retry-After` in whole seconds and `details: null`: `details` is for field issues, and a dialog that prints them would print "840" as a form line. The strict rate limit applies to the verify route.
6. **Recovery codes.** Ten codes of 15 symbols (75 bits) from a 32-symbol alphabet without I, O, 0 and 1, shown as `XXXXX-XXXXX-XXXXX`, stored as the plain SHA-256 of the normalised code, each working once. A keyed hash would die with `JWT_SECRET`, and the recovery code is exactly what lets a person in when the sealed secret can no longer be opened. A recovery code works during a lock: 75 bits cannot be guessed, while the lock is how someone who knows the password could keep the owner out. A wrong recovery code counts against the challenge (five end it) but not toward the person's lock, because it adds nothing to guard and would hand a password holder a second way to lock the owner. The accepted limit: someone who knows the password can lock six-digit entry again after each recovery-code sign-in with about ten wrong tries, so the owner spends one recovery code per sign-in until the ten are gone and then needs a reset. A second counter was not added. Instead the owner is told: the card and the sign-in page warn of a lock in the last 7 days (the column `lastLockedAt`).
7. **The demo sign-in skips the second step**, and the card says so in one sentence. It has no password, and a shared demo role must never be locked by one visitor's phone. A demo session may turn two-step on for its account, which then guards that account's password sign-in. The exception: a demo session cannot start setup for an account whose role holds `users.manage` (today the System admin alone). The administrator's reset is the only undo, it refuses the administrator's own account, and nobody else holds the permission, so a visitor could block that account for good. The check is on the permission, not the role name, so it follows area 4's matrix. Residual case: a person who signs in by password as the System admin, turns two-step on, and loses the phone and the codes has the same problem. That is a real person's own act, and the operator script of the follow-ups is for it.
8. **Turning it on ends that person's other password sign-ins**, not the one doing it and not demo ones. A refresh token from before stays valid by default, and someone who got in with only the password would keep that session for the refresh lifetime. A person who turns two-step on is saying a password is no longer enough. Demo sign-ins stay, because a shared account has many visitors in it and ending theirs would let one visitor sign everyone out.
9. **An administrator can reset another person's two-step** (`POST /users/:id/two-step/reset`, `users.manage`). It is user administration, like disabling a user, and the administrator still holds no permission to approve an SPR, a payment or a bank detail. It refuses one's own account, audits the refusal, removes the secret and the recovery codes, and ends every session of that person, demo ones too. The limit, plainly: a reset removes the second step, so an administrator who knows a person's password could then sign in as that person. Today every seeded account shares `DEMO_PASSWORD` (ADR 0012 item 12), so the administrator could already do so with no second step. A notice to the person is a condition of turning the reset on outside the demo stacks. The lost-phone ladder is: a recovery code, then another administrator's reset, then (the first follow-up) an operator script. The button on Governance, Users is area 4's page and is not in this story.
10. **Audit.** Every success and every refusal is audited with a reason. Summaries are fixed sentences that name no reason, because a summary is shown as written to every role that reads the trail, while the `reason` key in `changes` is hidden from all but the auditor. No code, secret, setup key, hash or recovery code is ever in a log line, an audit row, an error or a URL. Responses that carry a secret send `Cache-Control: no-store`.
11. **ADR 0012 item 5 is amended.** It said only `login` and `demo-login` are exempt from the CSRF token. The verify route also starts a session and has no `op_csrf` cookie yet, so it is `@SkipCsrf()` with the same JSON and origin check.
12. **The code field is a port of the bundle, not the bundle**, in `apps/web/src/components/kit/code-field/`. The pixel toggle and [ADR 0062](0062-a-day-night-switch-replaces-the-theme-menu.md) are the precedent for a pasted bundle. The repository is private, the author is asked before it or the demo goes public, and the component is a one-folder removal (`kit/code-field/`, and the step's and dialogs' use of it).
    - **Kept:** one real `<input>` (`inputmode="numeric"`, `autocomplete="one-time-code"`) under six drawn cells, the sliding ring, each digit rising in, the unfold and the fold to a "Verifying" pill with a spinner, the red shake and clear, the green "Verified".
    - **Changed:** no GSAP (CSS and a spring from `motion` for the ring), no shadow root, no embedded font (Geist through the tokens, tabular), icons from `lucide-react`, every word through i18n, light and dark by tokens, fluid down to 320 px without `transform: scale`, the whole field one target of 56 px, reduced motion honoured, real verification by the server, and no demo code.
    - **The missing constants, chosen:** unfold 250 ms (`--motion-slow`); a digit rises in 160 ms (`--motion-fast`); the ring is a spring, stiffness 260 and damping 28 (the tokens); the fold to the pill takes 220 ms (`--motion-base`); the shake is 240 ms; the green fill is 250 ms; the spinner turns once in 750 ms. The three holds are timers in the parent, not motion: "Verifying" at least 500 ms, red 900 ms, green 700 ms. Every transition stays within the 150 to 250 ms band, and a test checks it.
    - **The field opens at once**, with no "Enter code" pill first, because a tap costs a phone user time and delays the keyboard's one-time-code suggestion, which needs a focused input. The bundle's unfolding is kept as the entrance: the shell grows from the pill's width to full width once, on mount. Under reduced motion the field is simply shown.
    - **Lazy chunks.** The sign-in page is the entry page, so the step, the field and the setup dialog load as chunks of their own.
13. **The QR code is `qrcode.react` 4.2.0**, exact pin, `QRCodeSVG` only, black on white in both themes (a scanner needs dark modules on a light ground), in the setup dialog's chunk. It is ISC, has no dependencies, lists React 19 in its peer range, has no install script, and was released on 2024-12-11, so `minimumReleaseAge` and `trustPolicy` pass. It returns inline SVG, so no `blob:` or `data:` image is placed under the web CSP. `uqr` 0.1.3 is smaller, but is before 1.0 and its release followed a gap of nearly three years. `qrcode-generator` 2.0.4 is five times larger and would need the SVG written by hand. The setup key is always shown as text beside the code.
14. **An exception to [ADR 0061](0061-a-section-list-with-one-section-at-a-time-and-one-shortcut-registry.md) decision 4.** Every other choice there applies at once and is kept on this device with no Save. Two-step is kept on the server and changes through explicit steps, and the card says so in a footnote.

## Alternatives considered

- **A code by email.** Nothing sends email, and the demo addresses cannot receive it.
- **A `200` with a second answer shape for "second step needed".** It changes the login response schema, the generated type and `login()`, and a caller that ignores it could take it for a session.
- **Keyed recovery-code hashes.** They die with `JWT_SECRET`, which is when a recovery code is most needed.
- **Columns on `User`.** `AuthGuard` loads the user on every request and the list route returns whole rows, so a ciphertext would ride along on every one. A table of its own also lets a row lock serialise the counters without locking the user row.
- **The lock length in `details`.** It prints on any form that shows unmatched details.
- **A second counter for recovery-code wear.** The owner is told instead.

## Consequences

- Six error codes join the contract and every generated error enum gains them: a large mechanical diff in generated files.
- The entry chunk grows by a path string, a few error texts and a few lines (the pull request has the measured budget).
- Four new tables: `TwoStepSecret`, `TwoStepChallenge` and `RecoveryCode`, with enums for the status and the channel.
- An unreadable secret after `JWT_SECRET` changed has no screen of its own: a recovery code signs in and turns two-step off, and the person sets it up again.
- A demo visitor can lock a shared account's password sign-in, except for an account whose role holds `users.manage`. The demo stack's reset from its template clears the others.
- A run of the end-to-end spec that is killed between turning two-step on and off is healed by the next run, from a git-ignored state file. A run killed with that file wiped needs a database reset.

**Not built:** making two-step compulsory for a role, "remember this device", codes by email or SMS, passkeys, a notice to a person that their two-step was reset, the Governance button, an operator reset script. The last three are follow-up issues.
