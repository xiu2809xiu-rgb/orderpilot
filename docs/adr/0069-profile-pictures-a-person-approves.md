# ADR 0069: Profile pictures a person approves

- **Status:** Proposed. The upload, the AI step and the account screens are area 1's and the destination rule is area 4's, so Richie accepts or declines it in review.
- **Date:** 2026-11-25
- **Story:** [#381](https://github.com/xiu2809xiu-rgb/orderpilot/issues/381)

## Context

Richie asked for profile pictures with a standard: people might upload something inappropriate, so a picture must be AI-sensed or human-approved before it is used. OrderPilot's tagline, "AI reads, rules decide, people approve", settles the question. A picture is data a person chose, so fixed rules refuse a bad file, an AI check may describe it when the data rule allows that, and a person decides. The AI never approves, rejects or hides anything (CLAUDE.md, section 1).

The repository had no upload route until now: nothing accepts a file, no multipart parser is in use, and document upload is P-18. So this story also decides how the first upload works. Area 4's data rule (`ai-destination-policy.ts`) lets only synthetic data go to any provider, the mock included, and a picture a person chose cannot be proved synthetic.

## Decision

1. **AI describes, rules refuse, a person decides.** Fixed rules refuse a bad file outright. An AI check, when the data rule allows one, tells the reviewer what it sees. A person approves or rejects every picture. No model output changes a status: a flagged picture stays pending, and no route lets the check act. The test that proves it is in `profile-pictures-ai.test.ts`.
2. **The browser prepares the picture, and the server trusts none of that.** The browser takes the middle square, makes it 256 by 256 px, flattens any transparency onto white and draws it through a canvas into a JPEG, so camera data such as the place it was taken never leaves the machine. The person sees the result before sending. The server then checks the bytes again as if the browser did nothing.
3. **A raw body route, with no global parser.** `PUT /profile-pictures/mine` takes the JPEG as the request body (`Content-Type: image/jpeg`, 1 to 262,144 bytes). The controller reads the stream itself through `readBoundedBody`, after the four guards (throttle, session, CSRF, permissions) have run, and hands the service a `Buffer`. A global raw parser registered in `configure-app.ts` would buffer up to 256 KB for every caller before any guard, anonymous ones included. A body over the limit is a 413, also when it is chunked or its `Content-Length` lies, and `discardRest` reads and drops what is left, within a budget of 1 MB and 5 seconds, so a browser can read the 413. It first removes the `readable` listener that `readBoundedBody`'s iterator leaves on the request, because a stream with one stays paused; a test on a real HTTP request shows the rest being read. A body sent as more than 4,096 chunks is refused as too large, so tiny chunks cannot make the server hold one buffer each.
4. **A cleaner that keeps only the picture, and no image library.** `JpegCleaner` walks the file segment by segment and rewrites it from the parts it allows: it keeps the tables, the frame header and the scans it has checked, writes every marker as exactly FF xx, drops APP1 to APP15, comments and any APP0 that is not a bare 16-byte JFIF header (a JFXX thumbnail is a second picture), and cuts everything after the first end marker. It never repairs: a file that is cut short, or has anything between segments, is refused. It reads the size only from the frame header it walked to, never from EXIF or a thumbnail. It takes baseline and progressive JPEGs, square, 128 to 512 px a side, and it never decodes a pixel. `sharp` is native and the pure-JavaScript decoders decode pixels, which this never needs. A polyglot payload hidden inside valid scan data survives cleaning and is contained by the response headers (decision 9).
5. **States, and what is kept.** A picture is PENDING, APPROVED, REJECTED or REMOVED (withdrawn, replaced by a newer upload, replaced by a newer approval, or taken down, with which one recorded). A person has at most one pending and one approved picture, held by two partial unique indexes in the migration. The stored object of any picture that is no longer pending or approved is deleted, rejected ones too. The row keeps who, when, why and the SHA-256, never the picture. The delete happens after the transaction commits, and a sweep retries a failed delete after every review and withdraw commit, at start-up and at each upload.
6. **One lock per person, and a guard per person.** Every change to one person's pictures (upload, withdraw, approve, reject, take down) takes a row lock on that person's `User` row and re-reads the status under it, so two reviewers at once give one decision and one 409. A per-person guard in Redis (`SET ... PX 30000 NX`) is taken before the AI call and the storage write, so a second upload in flight is refused with `upload_busy`. A transaction lock cannot do that job, because it ends with its transaction and cannot span the AI call. If Redis throws, the upload goes on and the class and trace id are logged: the guard limits cost, not safety.
7. **Limits.** Ten stored uploads in any 24 hours, counted from the table under the lock: per session for a demo session, and only the uploads made with a password for a password session, so demo visitors of the same account never lock it. A file a reviewer rejected, or a take-down of it, sent again within 30 days is refused with `rejected_before`. Every upload refusal is audited with its code, sampled to one row per person and code a minute, so 200 junk files cannot fill the chain.
8. **The AI check.** Feature `profile-picture-check`: one image part, a zod schema for the answer (a verdict of "looks fine" or "needs a closer look", concerns from a fixed list of nine, a note of at most 200 characters), fixed trusted instructions, the picture as data. The call states origin `"real"`, because a person chose the file and nothing proves it is synthetic, and classification `confidential`: an unreviewed staff picture is personal data of staff, hidden from most roles until a person approves it, and `confidential` is the level the code gives to data a role does not see by default. Angelyn is asked to confirm the level. Nothing here labels a picture synthetic to get past the rule.
9. **Ask first, then call.** The service first asks `LlmGateway.mayReceive(context)`, a new method that returns only `{ allowed, rule }` and writes no audit row and no usage record. A "no" is recorded as "not checked by AI" with the rule's name, and nothing is sent. A port is not exported from the AI module on purpose, and `mayReceive` leaves `ai-imports.test.ts` unchanged. The service still handles a refusal from the real call, because the policy can change between the two steps. The call is raced against 5 seconds (`withDeadline`), made before the transaction because the gateway refuses to run inside one, and a slow or failed check is recorded as "not run": it never fails or holds an upload. A mock answer is recorded as "not run" with the reason `mock`, so a canned "looks fine" never stands beside a real person's face.
10. **Who reviews.** Whoever holds `users.manage`, which is the System admin today. No new permission, and nothing in the permission matrix or the AI destination rules changes. Reviewing a picture is user administration, as disabling a user is. The role table says the System admin "never approves": that still holds, because approving a picture is not approving an SPR, a payment or a bank detail. Nobody reviews their own picture: the server refuses and audits it (403 `own_picture`), and the review lists never hold the caller's own pictures, so the waiting count only counts what the reviewer can act on.
11. **How a picture is shown.** One `UserAvatar` part draws an approved picture or the initials, in the side menu and on the account card. The URL is `/api/v1/profile-pictures/{pictureId}/image`, keyed by the id of one stored picture. The route answers `image/jpeg` with `nosniff`, helmet's strict CSP, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: private, no-cache` and the SHA-256 as the `ETag`. It is `no-cache` and not `max-age` on purpose: a copy kept for a year in a browser would outlive a take-down. The server checks who may see the picture before it answers 304, and answers 404, never 403, for a picture a person may not see. An approved picture is served to any signed-in person, a pending one to its owner and to reviewers, and a disabled owner's to nobody.
12. **Demo sessions.** Every visitor of a demo role is the same account, so read literally "visible to its owner" would show a pending picture to every visitor of that role. A demo upload therefore stores the sign-in family (`sessionFamilyId`), a pending picture is shown only to the session that sent it and to reviewers, and the cap is per session. An approved picture is the account's, as any approved picture is.
13. **Refusals in the one envelope.** A picture refusal is a normal error envelope with `details[0].message` set to a machine code from `PICTURE_REFUSALS`, and the web turns the code into its own words. For a 413 there are no details, and the web maps the status to `too_big`. No new `ErrorCode` is added, which would ripple through the generated client and two shared tests.
14. **Audit.** Every action is an audit row on entity type `User` with the owner as the entity: uploaded, withdrawn, approved (with the replaced picture), rejected, taken down, each refusal, and each object the sweep deletes. A reason travels under `reasonCode`, never a key named `reason`, because the viewer masks that key for everyone but the auditor. No picture byte, base64 or URL is written to a row or a log.
15. **The Settings count, not a Home tile.** "Needs you" on Home is the person's workflow tasks from area 2, so a picture does not fit there. The "Profile pictures" entry in the Settings list shows a waiting count through the existing `useListCount` and `MenuCount`, and every decision refreshes it. No menu entry is added (ADR 0036). The review list has a pager and no row has a primary button.
16. **The binary routes stay out of OpenAPI.** The upload and image routes carry `@ApiExcludeEndpoint()` and the web calls them through `ApiClient`, with route constants in `packages/shared`. Nothing in this repository shows how orval renders a raw `image/jpeg` PUT, and `pnpm api:check` fails CI on any drift. The JSON routes are described and generated. `ApiClient` gained a raw-body path that sends the blob with its own type and the CSRF header, and sends the same blob again after a silent refresh.

## Alternatives considered

- **`sharp`, or a pure-JavaScript decoder.** Native code in the API image for a job that never needs a pixel. The cleaner reads headers and rewrites segments.
- **Multipart upload.** A parser nothing else uses, with its own limits and its own bugs, for one file of 256 KB.
- **A global raw parser.** It reads before the guards run (decision 3).
- **Signed URLs, or a URL per person that always gives the current picture.** A URL per picture id never changes its bytes, so the browser never shows a stale picture under a new id.
- **A queue job for the check.** The worker is P-15. It is follow-up 2.
- **A `pictureId` field on `Session`.** It would touch every role fixture and the generated client. The web reads its own query, `GET /profile-pictures/mine`, and `Session` is unchanged.
- **A Home tile for the waiting count.** It needs a cue in another area's feature file and a fifth tile in a grid of four.
- **`max-age` caching.** Outlives a take-down (decision 11).
- **Refusing uploads from demo sessions.** The feature would not be demonstrable. It stays the fallback: one condition in `PictureUploadService`.
- **An advisory lock for the in-flight guard.** It ends with its transaction (decision 6).
- **Showing the reviewer's own rows without buttons.** A count that included them would read "1 waiting" for ever for a lone System admin.

## Consequences

- **An approved picture is drawn only in its owner's side menu and on their card.** No other page shows it yet. Until follow-up 4 lands, the moderation protects only the owner's and the reviewers' screens. The owner's words say so ("Other pages do not show it yet"), and no string says that colleagues see it.
- **The AI check is built and tested, and it does not run under today's data rule.** Every row reads "Not checked by AI: only synthetic data may go to an AI tool", and the proposal demonstration shows the human step only. The check runs unchanged once area 4 allows it.
- **The check is not useful on a real provider before the queue job and a `signal` exist.** The 5 second race abandons a call that keeps running: it is retried up to `AI_MAX_ATTEMPTS` times at `AI_TIMEOUT_MS` each, billed, and its late answer thrown away.
- **Pictures follow whatever rule admits real `confidential` data.** The destination rule keys only on provider, origin and classification, so a later rule meant for real business documents would admit every staff photo. Follow-ups 1 and 2 are a gate: before the check is switched on, either pictures become `restricted` or the rule gets a feature allow-list. Spectra's written OK (A-31) is also needed.
- **The System admin's own picture cannot be approved by itself, and no other role holds `users.manage` by default.** The card says another administrator has to review it. Area 4 can give a second role the permission through the matrix.
- **A shared demo account shares an approved picture.** A pending one is shown only to the session that sent it. A visitor who signs in again gets a new family and no longer sees their earlier pending picture.
- **A polyglot payload inside valid scan data survives cleaning.** It is contained by `nosniff`, the CSP and the same-origin resource policy, and by serving only `image/jpeg`.
- **An API crash between the storage write and the commit can leave one orphan object.** The port has no listing, so nothing finds it. Follow-up 5 covers a sweep for objects with no row.
- **A request with `Connection: close` that is still sending a large over-limit body may see a reset before it reads the 413.** A browser keeps the connection and always reads it.
- **The entry chunk grows.** The route schema, `UserAvatar`, `useMyPicture` and the raw-body path in `ApiClient` are entry-chunk code. The pull request reports the measured figure.

## Not built

Drag-to-position cropping, drag and drop of a file, animated or PNG pictures stored as such, pictures on other pages (the users list, tasks, the tracker, the audit viewer), a "Take down picture" button on Governance, Users, a pill on the account menu's Settings item, a queue job for the check, a list of storage objects with no row, a history of every picture a person sent, compulsory pictures, picture-based sign-in, face detection and any image library.
