# ADR 0070: Availability on the avatar

- **Status:** Proposed. The shell, Settings and the sign-in options are area 1's, so Richie accepts or declines it in review. Angelyn confirms three things that are area 4's: the audit decision (decision 5), that the three routes carry no permission and sit outside her matrix, so no role can switch availability off (decision 4), and the classification (decision 7), which is documentation only because nothing in code carries it.
- **Date:** 2026-11-25
- **Story:** [#385](https://github.com/xiu2809xiu-rgb/orderpilot/issues/385)

## Context

Richie asked on 24 Nov 2026 for the Avatar Status Picker from LeiBox, a free component collection he used for the code field ([ADR 0068](0068-two-step-sign-in-with-an-authenticator-app.md)) and the day-night switch ([ADR 0062](0062-a-day-night-switch-replaces-the-theme-menu.md)). In the original, a glass status dot on an avatar expands into a pill of three choices (Online, Focus, Do Not Disturb) with a springy caption that follows the active choice. Arrow keys move, Escape closes, and a pick folds the pill back and sends a flash of light across the dot.

OrderPilot gets the idea and not the original. What the source says about rights: the design is by Nitish Khagwal (https://x.com/nitishkmrk/status/2121129936497111406/video/1). LeiBox's own record says "No separate license was supplied or verified for the original HTML and embedded avatar" and marks the source as not redistributable, and the site as a whole says it is for learning use only. No source text, markup, picture, font, colour or glyph drawing is in this repository. The part is built from a written description of proportions, spring feel and behaviour, and its header credits the designer and LeiBox. The repository is private ([ADR 0040](0040-what-going-private-changed.md)), and this is a private prototype for a school module.

Three things are stored or read: a person's own availability (set from their avatar in the side panel and from Settings, Account), a lookup of other people's availability by user id, and the sign-in options, which in demo mode must carry the demo accounts' ids so that a colleague's availability can be asked for at all. Decisions 1 to 9 are the server half (the table, the 12-hour rule, three routes, the ids in the options). Decisions 10 to 17 are the screens, which came in the same pull request.

The word is "availability", never "status": a status already means an order's status or whether an account is active. It is "Available" and not "Online", because OrderPilot cannot know that anyone is online. "Away" is taken too: `isAway` in the approval route is an administrator's dated leave window on an approver, and nothing here is related to it.

## Decision

1. **What it is and is not.** An availability is one of three values: Available, Focusing, Do not disturb. It is information for colleagues and nothing else. No reminder, escalation, Spectra's 24-hour rule, SPR routing or approval reads it, and a test (`availability-isolation.test.ts`, one in the API and one in the web app) fails when code outside the feature names the table, the relation, the shared names or the generated client. The test is a net and not a proof: a determined change can still reach it by a path the terms do not cover, and the test says so.
2. **One row per person; no row means Available.** The table `UserAvailability` is keyed by `userId` and holds only the two states that differ from the default (`FOCUSING`, `DO_NOT_DISTURB`) and `setAt`. Setting Available deletes the row, so a person who is available leaves nothing behind, and there is no history. Every `PUT` also deletes, in the same transaction and with the `setAt` index, the rows that are expired or stamped later than the clock plus its skew. There is no job. If nobody writes for a long time an expired row stays, at most one per person, and is never shown.
3. **The 12-hour rule is worked out when the row is read,** by a pure domain class (`AvailabilityRules`) that takes `now` as an argument. A row is live while `now - setAt` is under 12 hours (strictly: live at 11 h 59 min 59.999 s, Available at exactly 12 h). A row stamped later than `now` plus 5 minutes (the one tolerance in the feature, a named constant) is treated as expired, so a server clock that stepped back cannot hold a value beyond 12 hours plus the skew. `expiresAt` is always `setAt` plus 12 hours and is never capped. `now` comes from the `Clock` port of [ADR 0068](0068-two-step-sign-in-with-an-authenticator-app.md), provided again by the availability module so that a test can pass one fixed moment. The server stamps `setAt`; a client time is never read.
4. **The lookup answers every id alike.** `GET /availability?ids=` takes 1 to 100 comma-separated uuids (the precedent of the available-stock query) and answers one entry for each distinct id asked, in the order asked, with the lower-case id, the value and `setAt` and nothing else: no name, role or email. An unknown id, a disabled person's id, an id with nothing set and an id whose value expired give the same body apart from the id, so the answer is no oracle for which ids exist. Ids are lower-cased before they are made distinct, because `z.uuid()` accepts upper-case hex and the database returns lower-case ids. There is no route that lists everyone and no search, so the lookup cannot walk the directory. All three routes carry `@Authenticated()` on each handler and no permission: every signed-in person has an availability and may look up ids, so there is nothing for a permission to say, and area 4's matrix and `permissions.ts` are untouched. The `PUT` is limited to 30 a minute and the lookup to 120, on the clickstream write's precedent, and every answer sends `Cache-Control: no-store`, because it changes with the clock without any write. A request body that names a user (a `userId`) is refused: who is meant is always the caller of the session.
5. **A change is not audited.** The audit trail is for changes to records that matter: money, access, orders, stock, customers. By decision 1 nothing here is such a record, and the only actor is the person on their own value. The trail is permanent (a database trigger refuses `UPDATE`, `DELETE` and `TRUNCATE`) and, in History under Governance, Users, readable by every holder of `users.read`, so auditing would keep for ever a dated list of when each person said "Do not disturb": a record of staff behaviour that nobody asked for, and the "kept beyond need" that GRS risk R-04 names. Each write would also wait for the audit chain's lock, and [ADR 0012](0012-sessions-and-rbac.md) already leaves out a successful refresh for its volume. The fair case for the other choice: CLAUDE.md says "every sign-in, sign-out and change is audited", stories A and B audit all they add, a value that other people read can mislead and a row would be the only evidence, and if a rule ever reads availability the trail becomes mandatory. What would change this decision: any rule that reads availability, or Spectra asking for a record of it. The module does not import `AuditModule`, so a stray call is impossible by construction, and a test counts the audit events before and after a series of changes and checks that the chain still verifies. The guards audit what they audit today ([ADR 0012](0012-sessions-and-rbac.md), decision 8): an access token that does not verify is refused and audited, at most once a minute per client address; one whose session has ended or whose user is disabled is refused and audited; a missing or wrong CSRF token is audited when the caller holds a session or a refresh cookie; a call with no cookie at all is refused and not audited, and neither is an expired access token. Angelyn is asked on the pull request to confirm; if she says a change must be audited, one `audit.record` joins the upsert's transaction and the test is mirrored.
6. **Demo accounts are per account.** In demo mode every visitor of a role signs in as the same seeded account, so every tester of one role shares its availability, as they share its orders and tasks. It is the only choice with which the feature can be shown across roles, and the shared thing is a harmless label. The alternative, a row per demo session, needs a second key and a second read rule, makes a lookup of a demo account ambiguous, and needs cleaning of ended sessions.
7. **Classification: `internal`.** Any signed-in colleague may read it by design. It is never sent to an AI (the feature has no AI step), so no data-to-AI rule is touched. No code carries the level of a route or a table, so this is a label here and in the traceability row.
8. **The sign-in options carry the demo accounts' ids, in demo mode only.** Each `demoRoles` entry gains an optional `userId`. Without it the demo role menu cannot ask for a person's availability. It adds nothing a visitor cannot get: in demo mode anyone can already sign in as any of the accounts with no password and read the id from the session, and the page already lists their names and roles publicly. Outside demo mode the answer is `{ demoMode: false, demoRoles: [] }` as before, and a test proves it carries no id. The field is optional so that the sign-in page's fixtures and an account that is not seeded stay valid. `GET /auth/options` is a file Angelyn co-owns, so the pull request names her for it.
9. **Guards run in the repository's order** (throttle, auth, CSRF, permissions), so the `PUT`'s 429 comes before a 401 and a missing token on the `PUT` is a 403 `CSRF_INVALID`.
10. **The picker is a menu of three `menuitemradio` items on Radix, and not a radio group.** The trigger is a `button` with `aria-haspopup="menu"` and `aria-expanded`; the pill is a `role="menu"` named exactly "Your availability" (Radix names a menu by its trigger, which holds the old value, so the part passes `aria-labelledby={undefined}`); each choice is a `menuitemradio` with `aria-checked`, in one group. A radio group would send a write on every arrow press, because it selects as focus moves. A menu moves focus with the arrows and picks with Enter or Space, which is the original's own keyboard model and what a screen reader expects. Focus goes to the checked item on opening, by mouse and by keyboard, through `onOpenAutoFocus`, which Radix passes through but leaves out of the content's types, so it goes in by spread and a test guards it. After a mouse opening Radix may move the focus to the menu itself, when the pointer leaves an item that grew under it, and the sideways arrows then start from the ends: Right goes to the first choice and Left to the last, as Radix's own Down and Up do from the menu (the browser showed Left going to the middle one, and a test guards the pair). The four arrows wrap, Home and End jump, Escape closes with no change. Tab is held inside the menu, as in the shell's other Radix menus; the original closed on Tab, and keeping Radix's behaviour is a deliberate change. The part uses Radix's primitives directly, and not the wrapper in `components/ui/dropdown-menu`: the wrapper's entrance classes (`zoom-in-95`, `slide-in-from-*`, `fade-in-0`) cannot be cleared by tailwind-merge and would fight the pill's own animation.
11. **No button inside a button.** In the side panel the account menu's row is one button. The availability control is a second button, a sibling after it in the DOM, laid over the corner of the avatar by CSS (`.dx-person-row`, `.dx-person-dot`), so the row's name is unchanged and there is one dot. On a touch screen the control's box is 44 px but leaves the account button at least 24 px of the avatar (its left edge is 8 px inside the avatar's right edge, its top is the row's top), and in the 64 px rail it draws no overlay: a read-only dot, with the choice made in Settings. A tap on the avatar's centre therefore always opens the account menu. A read-only dot on someone else's avatar has no words beside it, so `useAvailabilityDot` gives `UserAvatar` the one sentence its screen reader reads ("Availability: Do not disturb"); the Demo role menu draws each value's words beside its dot and needs no second sentence. The shell's account menu is not edited. The dot's sheet sets no `position` on the dot or its button: it is outside Tailwind's layers, so it would beat the `absolute` utility that the profile card and `UserAvatar` pass, and a test fails if one comes back.
12. **Two skins, and a pill that grows out of its trigger.** A 14 px dot with a 2 px rim and a 10 px mark in the side panel; a 32 px glass ring around a 22 px dot (0.4 and 0.27 of the avatar, the original's proportions) on the 80 px avatar of the profile card. The pill's box is 166 by 96 px on a fine pointer and 266 by 98 px on a touch screen, which is its content (164 by 94 and 264 by 96: three 44 px orbs, 8 px gaps and padding and a caption chip on a fine pointer, three 80 px choices with their words on a finger) and the 1 px border on each side; it never exceeds `min(266px, 100vw - 16px)`, which keeps 8 px to the screen's edge. A box that left the border out would sit the orbs 2 px off-centre (8 px from one edge and 6 px from the other), and the caption is placed from the padding edge, so `chipPlace` takes the padding-box width, 164. It is in a portal, so the side panel and a phone cannot cut it, and Radix flips and shifts it with 8 px of collision padding. It opens with a negative `sideOffset` so that its near corner covers the trigger, and grows from there: the individual CSS `scale` property about Radix's own transform origin, on a spring written as a CSS `linear()` easing. There are two springs, both design tokens. On a fine pointer the pill grows on the pop spring, `--spring-pop-stiffness` 400 and `--spring-pop-damping` 28 (damping ratio 0.70, about 4.6 percent overshoot, 90 percent of the size at about 132 ms, the peak at about 220 ms, inside half a percent by about 350 ms): the browser measured no overshoot on the token spring (stiffness 260, damping 28, 0.41 percent), and the person who asked for the component knows the original's small bounce. These are OrderPilot's own numbers, chosen for those figures. A touch pill keeps the token spring (about 310 ms to settle), as a rule a test holds: Radix keeps the pill 8 px from the screen's edge (`collisionPadding`, the named `PILL_EDGE_GAP`), the pop's peak carries the fine pill about 6.2 px (ring) and 6.5 px (dot) past its box, which stays inside those 8 px, and the 266 px touch pill would pass them by about 10.2 px. The caption keeps the token spring too, so that it never overshoots the pill's edge, and reduced motion removes the growth as before. The pill's `opacity` is not on the spring but on its own 160 ms ease-out, because the spring's first 100 ms are almost nothing and a box that is still translucent shows the page's words through it. The trigger's face fades out while it is open, but only once the pill is in the page (the pill's part says so with `data-pill-open` on the trigger): the pill's code is a chunk of its own, and a slow or failed load must never leave the trigger blank. The caption is inside the pill's box and not a floating tooltip, so it can never leave the screen; it glides to the active choice on the token spring through `animate` from `motion/react`, and its first place and any change of width are placed at once. The spring library is fetched when the trigger is hovered or focused, or when the first pill opens, and not with the picker chunk, because the picker is fetched on idle on every page and the library was most of its cost (in jsdom, about 2 s on the first test of every file that draws the shell); a glide asked for before the library has arrived is a placement at once, and a failed fetch is forgotten and asked for again, with no error shown. The backdrop blur is on from the first frame. It was first switched on after the growth, to save repainting a scaled blurred box, and the browser showed the cost of that: the page's words showed through the growing box and then vanished with a jolt when the blur came on. `data-settled` still marks the end of the growth, for the tests. The words cross: the old word stays and fades out (160 ms in a straight line, `--motion-fast`: the 150 to 250 ms band and its test allow no shorter) while the new one fades in after a 60 ms wait, both centred in the capsule, so the capsule is never empty. The wait stays, because a longer word spilled out of the capsule's outline while its box caught up. The old word starts its fade from the opacity it had, worked out from the time since it arrived (the 60 ms wait, then the ease-out curve of `--ease-out`, whose numbers a test holds against the sheet and the tokens), so a quick move across the choices makes no word flash, and a word that had not yet become visible leaves nothing behind. It leaves the page when its fade ends, with a timer as a net for a tab that never fires the event, which is cleared when the pill goes; only one leaving word exists at a time, and under reduced motion, or where the kit holds still, there is none and the words change at once. On a touch screen the focus ring is drawn round the 44 px orb, as on a fine pointer, and not round the 80 px item, whose ring touched the pill's edges and cut through the words under the orb; forced colours follow. The dot on the account avatar of the side panel has its centre 90 percent across and 10 percent down (in the rail, 0.40 of the avatar's width from the middle): at 82 and 18 percent its rim covered the top of the second initial, and this place clears two initials and still overlaps the avatar's circle. The touch box of the open panel and the profile card's ring are not moved. What Edge measured on the final build, with motion on and a warm opening: the fine pill reaches 172.2 by 98.9 px from the ring and 172.5 by 99.3 px from the dot (the box is 166 by 96), 90 percent of its width at 140 to 158 ms after the press, its peak at 235 to 248 ms and its rest within half a percent by 351 to 368 ms; at the screen's edge, where Radix had shifted the pill to 8 px from it, the peak came within 1.85 px of the edge and never passed it; the touch pill never passed 266 by 98 px. The old word, fading on the ease-out curve, was below 15 percent by 50 ms and left the capsule with at most 10 percent of a word for four frames, so it fades in a line, and the most visible ink between the words is now 50 percent, with no word outside the capsule's outline in 28 changes by keyboard and pointer. On a finger the highlighted choice lifts about its orb and not about its 80 px box, or its ring came within 0.6 px of the pill's top edge; it keeps 1.7 px, as on a fine pointer. The first opening after a page loads showed a pause before a pill already near its size, about 100 ms for the ring and about 40 ms for the dot (headless Edge with a fresh profile). At that moment the trace shows a raster task of about 97 ms in the browser's GPU process (and 30 ms of shader work) at 32 ms, with no long task on the page, and the shell's own account menu shows the same on its first opening. The cause was not isolated, and it was left alone.
13. **Marks, tones and contrast.** Available is a tick on `--success`, Focusing a ring on `--warning`, Do not disturb a bar on `--destructive`; the mark is drawn in `--destructive-foreground` (there is no `--success-foreground`). No new token. The three silhouettes differ so that colour is never the only signal, and the words are in the item and in the trigger's name. A test reads `styles/tokens.css` and checks each mark on its tone at 4.5:1, each tone on the popover, the page and the pill's glass at 3:1 and the foreground on the glass at 4.5:1, in light and dark. The tones are also the order-status colours, so an amber dot can be read as a warning; the words and the mark are what say otherwise.
14. **What was not taken from the original** is the avatar picture, the font, every colour and glyph drawing, the avatar's growth by a fifth, the slide of the cluster, the rise of the anchor, the motion blur, the floating tooltip and the seven springs with their animation loop. What was kept is the idea: a glass dot that stretches into a pill of three choices, a caption that follows the choice with a spring, a flash of light after a pick, and arrow keys. Every movement is `scale`, `translate`, `opacity` or a `box-shadow` pulse; the pill's own size is never animated.
15. **It loads after the first paint.** The control in the entry is thin: the shell's own deferred dropdown (stand-in trigger, prefetch on idle, hover and focus, the hand-over of focus, ADR 0035) and a content part loaded as a chunk of its own. All the words are in `common.json`, the only namespace the entry loads, so the shell never suspends on them (a test renders the shell's entry parts with only `common` loaded). The files of the entry are added to `entryFiles`, so the lint rule guards them.
16. **Settings, Account.** The profile card's avatar is 80 px and carries the ring; the picture card's preview is now `size-16`, so the two avatars on the page differ. A row "Availability" says the value in words with its end ("Do not disturb, until about 3:40 pm") and has a "Change availability" button that scrolls the ring to the middle of the screen, opens the same menu on the ring (Radix allows one trigger per root, and the trigger is also the anchor, so the button cannot be a second trigger) and takes focus back to itself when the menu closes, to the ring when the ring opened it. A refused change goes back to the previous value and shows an alert with the message, the trace id and a way to try again. After a pick a toast says the choice and, for Focusing and Do not disturb, how long it lasts and that reminders and approvals still reach the person. While a change is saved the button is busy (`aria-busy`) and not disabled, and a press does nothing: the menu hands focus back to the button when it closes, and a disabled button would let it fall to the page. It is disabled only while the value is being read. The two controls that Settings draws for one person (the side panel's dot and the ring) read what is saving, what was refused and the pulse from one mutation key in the query client, so a later success from either one clears a refusal, Try again can only send the change that was refused and is still the newest, and a second change cannot start while one is saving. A refusal from before a control appeared is not shown by it. Undo is offered only for a change away from Available: the server stamps the time itself, so undoing any other change would start a fresh 12 hours and not restore the hours that were left. The 12 hours are also watched on screen by one timer for the end (never sooner than one second and never longer than a day), which asks again and, if the server still says live because the browser's clock runs ahead, waits 30 s, 60 s and so on up to 5 minutes. No string says that colleagues can see availability outside demo mode, because no screen shows it until the follow-ups land; the two sentences that say so are drawn only in a demo session, and a test fails any other.
17. **A choice is picked by a press and a release on that choice, or by the keyboard, never by a release alone, and one model says when a press counts.** Radix opens a menu on the pointer's press, and the pill grows out of its trigger, so the pointer is soon over the first choice (for the ring, over Available) with the button still down, and what follows the opening press (a release, a second click, the click of a finger's tap) lands on a choice that nobody chose. Radix's menu item answers a release it saw no press for by clicking itself (react-menu 2.2.1, `onPointerUp` of `MenuItem`), so a plain click on the ring would have picked Available. The model is written once, in `openingPress.ts`, and has two things kept in that module. The first is a clock that starts each time the menu opens, however it was opened (the control starts it when its open state turns true, so the profile card's button and a keyboard opening start it too), and whether or not Radix kept the pill mounted through a fold, which it does when a menu closes and opens again within the fold. The second is the pointer press that opened the menu, with its place (the trigger's pointerdown, including the shell's stand-in before the menu's code arrives), kept only when it will open the menu: not while a save is in flight, not with another button, not with the control key, not when the menu is open. The rules are these.

    - A press on a choice is refused in the first 250 ms of the clock, because the second click of a double click on the ring lands on the first choice (the browser showed a double click turning Do not disturb into Available at every gap from 60 to 350 ms) and no hand has chosen in a quarter of a second.
    - A press is refused too when it repeats the opening press: within 500 ms of it and within 8 px of its place for a mouse or a pen, 24 px for a finger, which never lands twice on one pixel. A person who chooses has moved the pointer or has waited; a person who repeats the click has done neither. The 500 ms is a fixed number, the usual double-click time. It does not read the system's setting, which can be longer (Windows allows up to 900 ms), and a slower double click picks. A repeat restarts the half second, so a burst of clicks at one place is one gesture and a triple click picks nothing either. But only for the first second after the opening (`OPENING_CLICK_MS`, the same second in which a click with no press is refused): the gesture that opened the menu lasts one second at most, and a person who keeps clicking because nothing seems to happen gets their pick as soon as that second is over, wherever it lands. Without that end, someone who clicked again and again, less than half a second apart, would never pick: each click would be refused and start the half second over.
    - A refused press stays refused: its release and the click that belongs to it pick nothing, however long the button is held (a press refused at 200 ms and held past a second used to pick).
    - What a choice keeps of a press counts only in the opening it was made in. The clock's module numbers the openings, a choice keeps the number with its mark ("may pick" or "refused"), and a mark from another opening is read as no press (a pick closes the menu, which ends its opening, so a pick needs no clearing of its own). Radix keeps the pill mounted when a menu closes and opens again within the fold, and a press that was slid away from never ends in a click, so nothing cleared its mark: a finger's tap on the trigger, in the next opening, sent its click to that choice and it picked, the very choice that the person had slid away from. A finger's tap on a choice still picks, because its pointerleave comes before its click and the mark outlives it within one opening.
    - A release never picks: every release on a choice stops Radix's own click, and a pick is the browser's click on the choice or the keyboard's. Radix marks every press on an item, and its click-on-release fires only for an item not pressed since it mounted, so a choice needs no memory of its own release. The price is that pressing a choice, sliding off it and releasing on another picks nothing, and the menu stays open.
    - A click made by a pointer (its `detail` is 1 or more) on a choice that was not pressed is the click of the tap that opened the pill, which a finger's tap sends to whatever lies under it after the release, and it is refused in the first second of the clock (`OPENING_CLICK_MS` = 1000). A finger held longer is a long press, which sends no click, and after that second a click with no press of its own picks, so that an input that sends one (a mobile screen reader, a browser not tried yet) is not refused for ever. The keyboard's click and one made by assistive technology have `detail` 0 and pass. The mark a press leaves outlives the release, because a touch screen's pointerleave comes before its click, and goes with a cancel, with the refusal of its click, or with the opening.
    - A held key picks nothing. Radix clicks a focused item for Enter and Space without reading `repeat`, so a held Enter picked the checked choice, closed the menu and gave the focus back to the trigger, and the next repeat opened the menu again. A choice ignores a repeated Enter or Space, and so does the trigger, with the menu closed. ArrowDown opens, and its repeat does no harm.
    - A pill that is folding takes no press (`pointer-events: none` on its closed state), so a press on it reaches what lies under it.

    The press expires by its own time and is forgotten when the control leaves the page (a test render saw its neighbour's press without that), so a pill opened later by the keyboard, or from a button that is not the trigger, is never held back by an old press. Component tests send the events in the browser's order (press and release on the choice, a release alone, a press, a leave and a release elsewhere, a finger's tap with its pointerleave before its click, a press in the quarter second, a press 400 ms after the opening press at its place and 60 px away, a finger's second tap 15 px away, a third click 300 ms after the second, clicks 300, 600 and 900 ms after the opening press and a click at 1200 ms that picks, a press refused at 200 ms and held for 1.5 s, a repeated Enter and Space, a menu closed and opened again with its pill kept mounted, a press slid away from and then a close and an opening within the fold). End-to-end tests press the ring for 120 ms with a real mouse, double click it at gaps of 60, 200, 320 and 400 ms, triple click it 300 ms apart, hold Enter, press again after a pause of 700 ms, and tap the dot and the ring with a finger.

## Alternatives considered

- **A row for all three values, with an Available row and its time.** It would keep, in a table, when each person was Available.
- **A scheduled job to delete expired rows.** F3 says no job, and a read must not write.
- **Deleting on read.** A `GET` that writes breaks caching and its own idempotence.
- **`POST` with a body for the lookup.** A comma list is the repository's precedent for many ids in a query, needs no CSRF header and is cacheable by the query client.
- **A 404 for an unknown id, or leaving unknown ids out.** Both let a caller tell a real id from an invented one.
- **Audit rows (`availability.set`).** See decision 5.
- **A route that lists colleagues.** It is a directory, which the lead forbids.
- **Per-session demo values.** See decision 6.
- **A radio group, a listbox, or the original's three toggle buttons.** A radio group writes on every arrow; a listbox shows the value as text and the trigger is a dot; the toggles tell a screen reader nothing about "one of three".
- **A floating tooltip above the pill, scaling the original down to a 32 px avatar, and putting the picker inside the account menu.** The tooltip is outside the collision box and can leave the screen; a scaled ring would have a 12.8 px diameter and a 0.24 px rim; the account menu is the existing row's button and the brief put the picker on the avatar.
- **`/users/:id/availability`.** `UsersController` has `GET :id` behind `users.read`, and a person who may not read users must still set their own availability.
- **Fake timers for the 12 hours.** They would also move the JWT expiry check and the argon2 timing.

## Consequences

- A new table, `UserAvailability`, with an enum of two states, and a relation named `personAvailability` on `User` (the name keeps it apart from `ITEM_AVAILABILITIES`, which is stock cover).
- `GET /auth/options` now reads the database in demo mode: one indexed query for the offered accounts' emails, on a route under the default throttle.
- **What this does not prevent.**
  - A colleague who polls keeps their own history. Any signed-in role holding an id can call the lookup up to its limit, and the answer carries `setAt`, so the exact time of every set and every renewal can be recorded by the caller. In demo mode the public options give all the ids to anyone. OrderPilot keeps nothing after a value ends and cannot stop a viewer from keeping what they saw. No screen may say that nothing is kept anywhere.
  - The request log holds a timestamped line for each call: method, the full URL (for a lookup, the ids asked about), the address, the headers other than the three that are redacted, the status and the request id. It holds neither the chosen value nor the user id of a `PUT`. A test checks that no log line holds the value.
  - The planned nightly backups and Postgres dead tuples, until vacuum, hold a row for a while after it ends.
  - No analytics event is added. A later change could add one, and the isolation tests forbid it for this feature.
  - The isolation net reads `.ts` files under `apps/api/src`, the app module line by line (only its import and its one entry in `imports` may name the feature) and the SQL files of the migrations (only this story's own may name the table). It does not read code outside `apps/api/src`: `apps/api/prisma/*.ts`, `services/*` and `packages/*`. It does not see a name that is built when the code runs (a model chosen by a string, a table name joined from parts), an HTTP call to the feature's own routes by a literal path from a worker, a view or trigger made outside the migrations folder or by a script run by hand, or a rule that reads a copy of the value kept elsewhere under another name. It also trusts the feature's own folder, which it checks only for imports of the audit, workflow, governance, checks, analytics, queue and worker code.
- An offline browser shows the last known value, on the dot and in Settings, until the next successful read. The server decides when a value ends, because a browser's clock can run ahead, so the page never falls back to Available by its own clock. The timer asks again at the end and then at 30 s, 60 s and so on up to 5 minutes.
- A person disabled while on Do not disturb keeps their row, as story B's pictures are kept: users are never deleted and re-enabling restores the account. The lookup reads through `user: { disabledAt: null }`, so a disabled person's value is never served; enabled again within 12 hours of the last change, it is live again.
- Two tabs writing at once: the last write wins and exactly one row remains (the primary key).
- A `PUT` of the same non-Available value renews the 12 hours (`setAt` and `expiresAt` move), so the route is safe to repeat but not idempotent in the strict sense.
- A change of server clock by more than 5 minutes into the past hides a row until the clock catches up or the next write deletes it. That is the cost of bounding a clock fault.
- Outside demo mode no colleague sees another person's availability until the screens of areas 2, 3 and 4 use the lookup: the approver group on a waiting SPR, who holds a task or a stuck step, and the Users tab. They are follow-up issues and no string says otherwise.

Availability is the second kept on the server, with two-step ([ADR 0068](0068-two-step-sign-in-with-an-authenticator-app.md) decision 14), because colleagues must be able to read it.
