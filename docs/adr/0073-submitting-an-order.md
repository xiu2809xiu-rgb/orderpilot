# ADR 0073: Submitting an order

- **Status:** Accepted. Azri is asked in the pull request to confirm the conditions on the handoff, and Angelyn to review the audit shape and the refusal rows.
- **Date:** 2026-11-26
- **Story:** [#411](https://github.com/xiu2809xiu-rgb/orderpilot/issues/411), P-114

## Context

P-49 lets a person enter an order and edit it while it is a draft. Nothing moves a draft on: no order made on the form reaches the workflow. ADR 0072 declared the port `OrderHandoff` that tells area 2 an order was submitted, and left it with no caller. This story is the caller. A person submits a saved draft, the order becomes `submitted`, and the order is handed to area 2 inside the same transaction.

Order status lives only in area 2's state machine. Submitting writes the order's capture state and calls the port. It never sets a workflow status.

## Decision

1. **Permission.** `orders.edit` stays the permission: Support and a Product Manager may submit, and the System admin never can. P-49 gave both roles the draft, and the brief gives neither role alone the order. **A condition on Azri's binding:** `OrderStateMachine.start` refuses a user actor who is not Support, so for a Product Manager's submit his class starts the workflow as a system actor and takes the requester from `submittedBy.userId`, as ADR 0072 says. A refused submit is audited by the guard as "refused changing a draft order", and the same words are used for the PI re-issue route that holds `orders.edit`. Angelyn is asked whether one phrase for both routes suits her.
2. **What makes a draft submittable.** In this order: it is a draft (a submitted order says "Order SO-... is already submitted." and a void one gets the draft rule's words; the state comes before the version, as in ADR 0047 decision 13); the shipment date is not before the order date; master data still knows the customer and every item by number. The constructor already holds the rest. **Not rules:** stock cover (a short order may be submitted, and the hold is area 2's), a non-zero total (the PO sets the price), and attachments (no document table). A short stock position and a zero total are warnings the person reads before confirming, never blocks.
3. **The route.** `POST /orders/:orderNo/submit`, status 200, body `{ version }`. It is not a PATCH, which is a content edit with a partial schema, and not a 201, because nothing is created. The version is the edit token of ADR 0047 and is the only thing sent.
4. **One transaction, in this order:** the guarded update to `SUBMITTED` (version up by one), then the port call, then the audit row `order.submitted`. A `DomainError` from the port rolls all of it back and is rethrown unchanged, so its status, code and message are the answer. Any other error is a 500 and leaves no row.
5. **A refusal by the workflow is audited after the rollback.** The audit row of the failed attempt would roll back too, so one `order.submit.refused` row is written afterwards, in its own transaction. It holds `refusedBy: "workflow"`, the refusal's code and the version, and no message: an area 2 message could one day name an amount, and ADR 0047 decision 14 keeps prices out of the trail. The trace id leads to the log line with the words. The row ends in `.refused`, so it appears among the refusals next to permission refusals. Its summary, which the audit viewer shows, reads "... submit of order X was refused by the order flow", so no word of ours reaches a person; `refusedBy: "workflow"` in the changes is data. Angelyn is asked whether she wants another suffix. The audit row is not written before the call, because the audit chain takes one lock for the whole trail and the port call would then hold it for as long as area 2's code runs. If the refusal row's own write fails, the person gets that failure and not the refusal: this is chosen, because an unaudited refusal is worse than a 500 on a double fault, and the order is a draft either way.
6. **What the audit keeps.** `order.submitted`: who, the order number, the line count, the two versions, `poVersionNo` and `workflowEffect` (`none` or `applied`, the port's answer). No total, unit price, line, customer or PO number. "who and when" is stored nowhere else: no column, no migration. The order page links to the Activity tab, which draws the order's operation log.
7. **PO version 1.** `poVersionNo` is the constant `FIRST_PO_VERSION` at a submit. P-89 replaces it with the stored version.
8. **The workflow's label on a submitted stored order** comes from area 2's exported `WorkflowOrderStatusReader`, read through `OrdersService` after filter, sort and paging, and for the one order of the detail route. Area 1 reads and never writes. Null means no workflow holds the order. It is done after paging because nothing filters or sorts on the label, and so the query is bounded by the page size. A failing reader is not caught, in the list or in the read-back after a submit: this is chosen, because a swallowed failure would say "No team has a task for it" of an order that a team may hold, and after a committed submit the caller gets that error while the order stays submitted. Area 2's flow route cannot answer "not in the workflow": it is not found for any number outside the synthetic data.
9. **What changes elsewhere.** Master data lists a submitted stored order as an open order, so the customer's open-order count goes up and the item pages list it with its quantity to ship. Stock figures do not move and nothing reserves stock, so two submitted orders can claim the same stock. A Warehouse user sees a to-ship count with no task behind it until area 2 binds its class. Master data keeps showing the capture-state word "Submitted" while the Orders list shows the workflow's label, because the overlay is in `OrdersService` and not in the directory.
10. **The page for a stored submitted order with no workflow status** must not contradict itself. One stage word, "Not in the order flow", is used for it in the list, the page, the peek and the board column, and the draft's old "Not started" becomes the same words. Held at reads "Nobody". The status card says stock is information, not a hold. The Documents and Checks tabs say that an order typed in here has no PO file and is not checked. The notice says it is submitted, not approved, and that no team has a task for it. The page never says "yet", so it stays true for the orders in decision 14: the Journey card of such an order says "This order has no journey: it is not in the order flow." Held at says the same thing in the list, the peek and the page: "Nobody" for such an order, "Not set" for a draft, a void order and a stored order that a team holds but the tracker does not name. The board draws a last column for each kind of order with no step, under its own word and only when it has rows: "Not started" for a sample, "Not in the order flow" for a stored order that no team holds, and "In the order flow" for one that a team holds. No string says "workflow" to a person.
11. **A confirmation.** The step cannot be undone in this build, so a dialog asks first, with focus on "Keep editing", no keyboard shortcut and no Undo. It says only what is true whoever takes the order afterwards: it does not promise or deny what area 2 does. Short stock and a zero total are warnings in it.
12. **Honest failure words.** "It is still a draft." is said only for an enveloped 4xx answer that is not a 409 or a 404, which proves the transaction rolled back, and the button to submit again stays. Every 409 and 404 shows the server's own sentence and claims nothing about the order, because the same status covers a stale edit token, an order someone else submitted meanwhile, a refusal by the team that takes the order next, and an unknown order. Its one action is "Reload the order", after which the dialog does not strand the person: if the order is still a draft, the dialog shows its first view again with the new edit token and "Submit order" available, and if it is no longer a draft, the page is replaced and the dialog is gone. For a 5xx or a network error the dialog says the result is unknown, offers the reload and asks the server again by itself, and the notice takes focus if the order turns out to be submitted. A 400 that names fields closes the dialog and puts each issue on its field; a 400 that names none, such as a refusal by the workflow, is a sentence in the dialog. A failure is announced once, by the block's alert role, and focus goes to the first action of the failure view. A dialog does not send what belongs to a previous person if someone else signed in over the page, and it closes when a request settles after they did. The dialog has no close button: "Keep editing" is the way out.
13. **No way out for a wrong submit until P-50.** The page says plainly that OrderPilot cannot change or cancel a submitted order, that its PO number stays with it, and that a corrected order needs a different PO number.
14. **Orders submitted before area 2 binds its class** get no workflow, and nothing hands them over again: the port is called once per submit. No sweep is built here. Azri and Richie choose one of two ways out when binding: a one-off script that calls `submitted` again for submitted stored orders that have no workflow (the port treats the same call twice as one), or a reset of the demo data submitted before the binding.

## The contract for Azri

| When or what       | The rule                                                                                                                                                                                       |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| When it is called  | Inside the transaction. The order row is already `SUBMITTED` but not committed                                                                                                                 |
| `request`          | The same ip and trace id as the audit row                                                                                                                                                      |
| A 0% prepayment    | Arrives as `"0.00"`. His `start` must turn it into no prepayment due, or it refuses with "The prepayment due must be an amount above zero, or none at all." and the person reads that sentence |
| A free PO          | Arrives as total `"0.00"`, the same rule                                                                                                                                                       |
| Currency           | None on the fact: prices are USD. A field can still be added while the port is unbound                                                                                                         |
| A refusal          | A `DomainError` whose words go to the submitter, whatever their role may see: no price, total or bank detail                                                                                   |
| Its codes          | `CONFLICT`, `VALIDATION_FAILED` or `FORBIDDEN` are shown as given. Any other code shows generic words and the trace id                                                                         |
| His own audit rows | They precede `order.submitted` in the trail                                                                                                                                                    |
| Duration           | The worst case must fit Prisma's default, about 5 s, which a second submit waiting on the row also spends, or `Database.transaction` gets a timeout first                                      |

## Consequences

- A submit cannot be undone until P-50, which brings the cancel and expects to add a third call to the port.
- Two submitted orders can claim the same stock: nothing reserves it.
- The tracker stays blind to stored orders, so the order page does not ask it, or the flow route, for a stored submitted order with no status. When a status exists the page asks again by itself.
- Orders submitted while the stand-in is bound are orphans (decision 14), and ADR 0072's `poVersionConfirmed` answers `none` for them, so P-89's revise does nothing for them either.
- The end-to-end test leaves submitted orders behind, with a fresh PO number each run.
- The audit trail reads `order.submitted` after area 2's own rows for the same click, because the audit row is written last.

## Alternatives considered

- **A new permission `orders.submit`, held by Support only.** It would touch the permissions file, the matrix, the refusal wording and two governance tests, and the brief gives a Product Manager the order too.
- **Probing area 2's flow route** to learn whether a workflow holds the order. It answers not found for stored orders, so it gives the wrong answer exactly when it matters.
- **Storing who submitted and when** in two nullable columns. It needs a migration and a name lookup, and the audit event already holds both.
- **Writing the audit row before the port call,** so the trail reads in causal order. It would hold the audit lock across area 2's code.
- **One click with no dialog.** Rejected because the step cannot be undone here.
