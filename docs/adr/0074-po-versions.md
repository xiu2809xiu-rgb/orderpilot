# ADR 0074: PO versions

- **Status:** Proposed. Azri reviews the call to the port and the lock order, Angelyn reviews the triggers, the audit rows and the masking, and Iok Teck reviews the one optional field on the check result.
- **Date:** 2026-11-26
- **Story:** [#227](https://github.com/xiu2809xiu-rgb/orderpilot/issues/227), P-89

## Context

A customer who revises a PO sends a new PO that keeps the old number, and Spectra calls it version 2 of the same order (5 Nov briefing, assumption A-39). ADR 0072 fixed the name `poVersionNo` and the port `OrderHandoff`, whose second call `poVersionConfirmed` tells area 2 that a revision was confirmed. ADR 0073 made a draft submittable, so a stored order can now be submitted. This story is the caller of the second call: a person confirms that a re-sent PO revises a submitted order, the earlier version is kept, and the order moves to the next PO version.

Order status lives only in area 2's state machine. Confirming a revision writes the order's content and calls the port. It never sets a workflow status.

## Decision

1. **The name.** `poVersionNo`, an integer from 1, read as "PO version 2" on screen. `version` stays the order form's edit token (ADR 0047 decision 5). A confirmed revision moves both numbers by one, so a guard written on `version` can never win over a revision.
2. **Storage.** The order row stays the current version. A version that a later one replaces is copied out, once, into `SalesOrderPoVersion` and `SalesOrderPoVersionLine`, and never changed. A copy holds the order date, the shipment date, the currency, the prepayment percent, and for each line the item number, description, quantity, unit price and quantity to ship, with the time and the person that superseded it. The plan's `externalDocumentNo`, `supersededByPoVersionNo` and `createdAt` columns are dropped: the PO number never changes in a revision, the next number is always n + 1, and `createdAt` would equal `supersededAt`.
   - **Read live, never copied:** the customer name, every person's name, the Business Central number, the PO number and the total. The total is derived from the lines through `SalesOrderLine.amount` and is never stored.
   - **Who and when.** Version n above 1 arrived when copy n - 1 was superseded, and by whom. Version 1 arrived when the draft was started, by whoever started it, so it is worded "Draft started": any person may edit a draft and a third may submit it, and the submit time is in the audit trail.
3. **Triggers and checks.** One function refuses a change, and one `BEFORE UPDATE OR DELETE ... FOR EACH ROW` trigger per copy table uses it. The foreign keys are `RESTRICT`, so an order that has a copy cannot be deleted. `poVersionNo >= 1` is a CHECK on the order and on both copy tables. Two deferred constraint triggers (after an update of the order's `poVersionNo`, and after an insert of a copy) make sure that at commit the copies of an order are exactly versions 1 to `poVersionNo - 1`. Only the revise move satisfies that, so a later writer that bumps the number, or adds a copy, alone fails at commit. P-50's cancel must keep the guard.
   - **TRUNCATE is not guarded, on purpose.** The copies live and die with their orders, which are not guarded against TRUNCATE either (a `TRUNCATE ... CASCADE` of the order table takes the copies with it), and the test harness empties every table with TRUNCATE. A database test shows that it goes through, so nobody believes otherwise. As ADR 0010 says of the audit table, a trigger stops mistakes, not the owner of the table.
4. **Only a submitted stored order has a PO version.** A draft is edited in place and nothing is copied when it changes, so a "version 1" of a draft would be other bytes tomorrow. A void order is always a draft that was never submitted. A read of the versions of a draft or a void order is a 409 with one detail, `captureState`, and a sample is a 404. The order detail's `poVersionNo` is null unless the order is submitted.
5. **A revision keeps the order.** The route is closed to another customer and to another PO number (400), and to content identical to the current version (400 on `revision`; the preview answers 200 with `identical: true`). The PO number is compared after the spaces are collapsed and the letters are upper-cased in JavaScript, while the index uses Postgres `upper()`; the two can differ for exotic letters. That is not fixed: the head keeps its own PO text, so the index can never be hit by a revision, and the cost is a second refusal reason.
6. **The guard.** The body carries `expectedPoVersionNo`. In one transaction, in this order: lock the order row where the number and the state match (`SELECT ... FOR UPDATE`), read the locked row, insert the copy, move the head with an `updateMany` that repeats the guard in its WHERE and moves `poVersionNo` and `version` together (a count other than 1 is an error), then replace the lines. Two confirmations at once give one 201 and one 409. The update is not first, because then the old header would be gone before it could be copied, and the copy is read from the locked table so that it is what the table held, not what the service believed. The reads are stable: `headOf` and `historyOf` re-read the number after their statements, and because it only grows, equal numbers prove that no revision committed between them. On a difference they repeat once, then throw.
7. **Routes and permission.** `GET /orders/:orderNo/po-versions`, `.../po-versions/diff`, `.../po-versions/:poVersionNo`, `POST .../po-versions/preview` and `POST .../po-versions` live in a second controller, so P-50's edits to the orders controller do not collide. Reads need `orders.read`, and preview and confirm need `orders.edit`, with no new permission. The refusal wording for `orders.edit` ("changing a draft order") now covers routes that are not about a draft, and Angelyn is asked whether one phrase suits her.
8. **One differences class and one view builder.** `PoVersionDiff` compares two contents. Lines pair by item number, never by line number; within one item the k-th of one side pairs with the k-th of the other in line order; leftovers are removed (earlier) or added (later). Decimals compare as numbers, so 5 and 5.000 are the same. The description and the quantity to ship are never compared. A line that only moved to another line number is not changed, but it makes the versions not identical. `toDifferencesView` is the only place a price becomes a masked object, and it builds its own diff from two contents and the role, so a caller cannot hand it a diff built with the wrong flag. Preview, confirm and the read route all call it, so the differences a person previewed are the ones stored and the ones read later.
9. **Masking is the server's.** A role that may not see prices gets `{ masked: true, field, classification, reason }` for every price of a version and of a difference, and no `from`, `to` or `changed` for a price. A line's status, `identical` and the counts come from the non-price fields for that role, and `pricesCompared` says so. A masked writer cannot change a price (the draft rules keep its stored price), so "identical" is exact for them too.
10. **Audit.** `order.po_version_confirmed` holds who, the two PO version numbers, the two edit tokens, the line count, the names of the changed header fields (never the total), the counts of added, removed, changed and moved lines, and the port's effect. A refusal by the port is written afterwards, in its own transaction, as `order.po_version_confirm.refused`, with the refusal's code, the two numbers and no message, and its summary reads "refused by the order flow". It ends in `.refused`, so it appears with the refusals and not on the order's Activity tab. No audit row, log line, toast or error message holds a price or a total. A Prisma error from the writes is caught in the repository and rethrown as a plain error that names only the order number, the PO version number and the Prisma code, because Prisma's own message can quote the arguments of the failed call.
11. **The port is called inside the transaction,** after the order is locked and moved and before the audit row, with the fact of ADR 0072 and nothing more. A `DomainError` from it rolls back the head, the copy and the lines, and is the answer; a plain error is a 500 and leaves nothing and no row.
    - **The contract for Azri.** The call is made with the order row locked and already updated, uncommitted. The lock order is the order row, then his rows, then the audit chain, and he never locks an order row. `request` is the same ip and trace id as the audit row. A total of `"0.00"` and a prepayment of `"0.00"` arrive as such. A refusal's codes `CONFLICT`, `VALIDATION_FAILED` and `FORBIDDEN` are shown as given, and its words are the only explanation the person gets, so they must name the reason and the next step and hold no amount and no "workflow". A slow call holds the order row, and a transaction timeout is a 500 with nothing saved. A revision is allowed at every stage here, so a stage that forbids one is refused by his side.
12. **The duplicate rule is amended in text only.** A PO with the same customer and PO number as a submitted stored order becomes its next PO version only when a person confirms that it revises the order. Otherwise `POST /orders` stays a 409 that names the order. The unique index, `findLiveByPo`, `nameTheWinner` and their tests are untouched.
13. **The check result gains one optional field,** `poVersionNo`, so that a result can say which version it ran on. Null or missing means it was not recorded: no check has run on a stored order, and a sample's results leave it null.
14. **A revised PO with a new number is a separate order** that nothing links, until Spectra answers Q-43.
15. **What a person is told after a confirmation.** The response carries no `workflowEffect`; the audit row does. Whether anybody was told is read from data (`workflowStatus` is null: no team holds the order), so it stays true after a reload and whoever binds the port.
16. **What changes elsewhere.** A confirmed revision replaces the head's lines, with `qtyToShip` equal to the new quantity. Master data lists a submitted order's lines by `qtyToShip`, so the customer's open orders and the item pages move with the new quantities. Available stock does not move and nothing is reserved. The Orders list's total follows the new lines, and the tracker, the checks and the workflow, which read the dataset, do not move. Once a shipment story lowers `qtyToShip`, a revision would restore the full open quantity and the copy keeps only the old value, so that story decides it.
17. **`FIRST_PO_VERSION` is replaced.** A submit hands over the order's own `poVersionNo`, and a draft is always at 1.

## Consequences

- Orders submitted while the stand-in is bound are orphans: `poVersionConfirmed` answers `none` for an order whose workflow was never started (ADR 0072 decision 8, ADR 0073 decision 14).
- P-50's cancel must keep both guards (`version` and `captureState`). Whoever adds a column to `SalesOrder` or `SalesOrderLine` classifies it in the drift test, as copied or as left out with a reason, or that test fails.
- P-55 may add a nullable source-document column to the order and its copy.
- A demo reset must TRUNCATE: the row triggers allow it, on purpose.
- Nothing deletes a version. There is no reason or note field, so a wrong confirmation is corrected by confirming another version, and the earlier ones stay.
- A copy carries no content hash, so an owner who drops a trigger leaves no trace. That is the same limit as ADR 0010, without the audit chain.
- `supersededAt` is the application's clock and the head's `createdAt` the database's. The two run on one host in every deployment we plan.
- The same Support user or Product Manager may revise as often as they like, and the audit row holds no direction of the total. Whether a price change needs a second person or a limit is Angelyn's question.

## Alternatives considered

- **A JSON snapshot column.** Rejected: typed columns and a drift test keep the copy and the order in step.
- **The version in the unique key.** Rejected: the duplicate rule stays as it is.
- **A digest of the previewed differences.** Rejected: confirm builds its differences through the same function as the preview.
- **`INSERT ... SELECT` for the copy.** Rejected: the types and the column mapping stay in one language, and the drift test guards both.
- **A new permission.** Rejected: Support and a Product Manager hold the draft, the submit and the revision alike.
- **A new 409 detail on the duplicate.** Rejected: the rule is not amended in behaviour.
- **A TRUNCATE trigger with an edit to the test reset.** Rejected, decision 3.
- **Prefilling the New order form's header from the stored order.** Rejected for now: the panel shows the header's differences first, and the form's own values are not changed here.
